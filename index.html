1. What is Infrastructure as Code, and which problems of manually created infrastructure does it solve?

Infrastructure as Code (IaC) means managing infrastructure using machine-readable configuration files instead of creating and configuring resources manually.
- Avoid manual configuration to enforce consistency
- Deliver stable test environments rapidly at scale
- Use declarative definition files

In my Week 1 VM setup, I had to create and configure the VM manually. With OpenTofu, the VM, network port, security group, security rules, key pair and floating IP can be described in code and recreated consistently. This reduces repetitive manual work and makes the infrastructure easier to reproduce and document.

Source: https://learn.microsoft.com/en-us/devops/deliver/what-is-infrastructure-as-code

2. Declarative vs Imperative Automation

2.1. Difference between declarative and imperative infrastructure automation

Declarative and imperative infrastructure automation differ in how they describe the process of managing infrastructure
Declarative automation describes what the desired final state should be, while the tool decides which actions are needed to achieve it. OpenTofu is declarative because my configuration describes resources such as a VM, network port and security group, rather than giving exact commands for creating them.
In contrast, imperative automation describes the exact steps that should be performed. For example, a shell script could contain commands to install Apache, enable the service and start it. Declarative automation is useful for infrastructure because I can describe the desired state and let OpenTofu calculate the necessary changes.

2.2. What does idempotency mean, and why is it important?

Idempotency means that applying the same configuration repeatedly should result in the same desired state without causing unnecessary changes or creating duplicate resources. This is important because infrastructure automation needs to be predictable, repeatable and safe.
In my Week 7 project, after the infrastructure already matched my OpenTofu configuration, running tofu plan showed “No changes. Your infrastructure matches the configuration.” This means OpenTofu recognized that the desired state had already been reached. Idempotency also makes rebuilding easier: after using tofu destroy, I could run tofu apply to recreate the infrastructure from the same configuration instead of manually repeating every setup step.

3. What is the state file used for? Why should it not be committed to a Git repository, and how do teams usually share it instead?

3.1. What is the state file used for?

The OpenTofu state file is used to keep track of the infrastructure managed by OpenTofu. It stores information about resources that have been created, such as the VM, security group, network port and floating IP. OpenTofu uses the state to compare the current infrastructure with the desired configuration in the .tf files. This allows tofu plan to determine what needs to be created, changed or destroyed. Without state, OpenTofu would have much more difficulty tracking the resources it manages.

3.2. Why should it not be committed to a Git repository, and how do teams usually share it instead?

The state file should not normally be committed to a Git repository, especially a public one. It can contain sensitive information or detailed information about the infrastructure and resources. Committing it can therefore expose information that should not be shared publicly. The state file can also change frequently whenever infrastructure is modified. Keeping it in Git can cause unnecessary conflicts when several people work on the same project.
In a team, the state is usually stored in a remote backend instead of being kept only on each developer's computer. A remote backend allows team members to access the same state when running OpenTofu. It can also provide features such as state locking, which helps prevent two people from modifying the same infrastructure at the same time. This makes collaboration safer and keeps the team's infrastructure state consistent.

4. What is Configuration Drift, how does it happen, and how does an IaC tool detect it?

4.1 What is Configuration Drift ?

Configuration drift happens when the actual infrastructure becomes different from the configuration defined in the Infrastructure as Code files. The desired state is described in files such as main.tf, but someone may change the real infrastructure manually. Over time, these differences can make the infrastructure inconsistent with the code. Drift can happen because of manual changes, emergency fixes, or changes made by another system or administrator. This is one reason why IaC is useful for keeping infrastructure consistent.

4.2 How does it happen, and how does an IaC tool detect it?

In my Week 7 experiment, I created configuration drift by manually deleting the HTTP port 80 security group rule from the OpenStack web interface. The rule was still present in my main.tf, so the desired configuration said that the rule should exist. However, the actual OpenStack environment no longer had the rule. This created a difference between what OpenTofu expected and what actually existed in the cloud environment.
OpenTofu can detect this difference when running tofu plan. It compares the desired configuration and the information recorded in its state with the actual infrastructure. In my experiment, tofu plan detected that the HTTP rule was missing and proposed to add one resource. The result was Plan: 1 to add, 0 to change, 0 to destroy. This showed that OpenTofu could detect the configuration drift and propose a way to bring the infrastructure back to the desired state.

user_data is used by cloud-init during the VM's initial boot to configure the machine. In this case, it is used to create the web page and install/configure Apache. Cloud-init is not intended to continuously apply changes to user_data on an already-running VM. Therefore, when user_data changes, OpenTofu must recreate the VM so that cloud-init can run with the new configuration.

Therefore, replacing the VM did not necessarily mean that the floating IP resource itself had to be replaced. In this apply, the same floating IP was retained, so the public IP remained 86.50.231.203.

The new public IP was: 86.50.252.42 The previous public IP was: 86.50.231.203 Therefore, the public IP changed after the destroy and re-create operation. Destroy order:
The actual destroy order was determined by the dependencies between resources. OpenTofu uses its dependency graph to determine which resources must be removed before the resources they depend on. For example, the floating IP depends on the network port, and the VM is connected through the network port. Security group rules also depend on the security group. Therefore, dependent resources must be removed before their dependencies.
Why did the project network survive?
The project network was not destroyed because it is declared as a data source: data "openstack_networking_network_v2" "project" The data source only reads information about an existing network. OpenTofu does not own or manage the lifecycle of that network, so tofu destroy does not delete it.
Why does a changing IP address matter less when there is an output?
The IP address can change when the infrastructure is recreated, but the OpenTofu output automatically shows the current address: web_server_url Therefore, I do not need to manually search for the new IP address after every rebuild. If the address had to remain the same, I would need to use a persistent floating IP that is not destroyed and recreated together with the rest of the infrastructure, and then attach that existing floating IP to the new server.
